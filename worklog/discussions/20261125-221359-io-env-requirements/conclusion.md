# IO_ENV 要件・仕様の整理

## 合意済み
2026-11-25 にユーザーから、カメラは1台以上、IO_ENV は Linux ベースのコンテナで動作させるとの条件を受領。複数カメラの同時利用の具体的な上限・構成は未決。

ユーザーは X Window によるリアルタイム表示を候補に挙げ、WSL 上の Docker で USB デバイスを認識する手順書を後で作成するよう依頼した。表示方式は提案段階。手順書は後続作業であり未作成・実機未検証。

ユーザー指定: OpenCV を介してキャプチャーボードやカメラの映像を取得できるようにする。表示は1ウィンドウ。複数入力を同時にどう表示するか、対象機器・バックエンド・設定方法は未決。

IO_ENV はカメラ映像を取得し MOT_ENV に提供、MOT_ENV の最新追跡結果の BBOX と Track ID を映像に表示する。表示は結果と映像の同期を待たず時間差があってもそのまま表示する。映像保存の有無を設定でき、有効時は取得フレームを JPEG で連続保存する想定。MOT が飛ばしたフレームも保存対象。日付とフレーム番号による整理、コンテナログの蓄積先も既存方針。出典: [現在の要件](../../../agent_log/requirements.md)。

## 提案・未承認
- 利用者: 追跡を観察する操作者、記録から挙動を調べる開発者。取得・提供・表示・保存・ログを IO の責務とし、Track 管理と SOT 制御は MOT の責務とする。
- フレームと結果の出所、識別、時刻、寸法・座標系を照合可能にする。実行・カメラ・フレーム ID の具体仕様は未定。表示自体は同期を待たない。
- 保存対象は IO が取得したフレームとし、MOT 向け間引きより前から扱う。カメラが生成したが IO が取得できなかったフレームまで保証しない。
- カメラ断、MOT 断、結果の順序逆転、保存失敗、再接続を区別し、何が起きたか確認できるようにする。各場合の継続・停止・通知は未決。
- 模擬入力・MOT で取得、非同期表示、保存 ON/OFF、MOT の間引きを検証。取得・保存成功の集合を比較し、遅延・逆順・障害注入は仕様決定後に合否を定める。実カメラ・ストレージの試験も必要。
- OpenCV が利用する入力機器・複数台構成、表示方法、性能目標、保存負荷、通信、結果新旧の定義はユーザー確認と後続設計が必要。USB の採用は固定しない。

## 比較とリスク
保存不足時の停止は異常を明示できるが運転が止まり、取得待機は入力側欠落や遅延を生み得る。欠落を許して継続する案は既存の取得フレーム保存方針の変更を要する。いずれも未決。結果を受信順に採用すると順序逆転で表示が巻き戻る場合がある。有限バッファや最新優先、入力の分岐・通信方式は設計候補で確定しない。
