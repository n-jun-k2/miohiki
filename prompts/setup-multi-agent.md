# マルチエージェント開発環境の構築指示

## 入力
- 対象：現在の作業ディレクトリのプロジェクト（別途指定があればそのパス）
- 目的・技術領域：既存資料とユーザーの指示から把握する。未確定事項は確認する。

## 目的
異なる専門性と判断基準を持つサブエージェントが独立して検討し、相互に反論・再検討した上で、メインエージェントが回答を統合する環境を構築する。

## 事前調査
既存の AGENTS.md、Agent、Skill、要件・設計資料、リポジトリ構成、Codex CLI のバージョンを確認する。利用可能な機能と設定形式は公式ドキュメントで確認する。既存の決定・設定を無断で上書きしない。

## Agent設計
プロジェクトに必要な役割を選定する。初期候補は要件分析、技術研究、ドメイン専門家、アーキテクト、評価・検証、批判的レビュー。例えば MOT なら mot_researcher、algorithm_engineer をドメイン固有の役割として検討する。
各 Agent に責務、判断基準、入力・出力、責務の境界、禁止事項を定義する。不要な役割は増やさない。議論担当は原則読み取り専用とし、実装や要件確定を行わない。

## Skill設計
- flow-requirements：要求の抽出、ヒアリング、要件案とレビュー。
- flow-discussion：技術課題の独立検討、相互レビュー、再検討、統合。
- flow-design：承認済み要件に基づく設計案の比較とレビュー。
自然文の議題または資料パスを入力とする。共通の議論手順は flow-discussion に集約し、他の Skill から参照する。

## 議論手順
1. メインが議題、制約、関連資料を整理し、必要な Agent を選ぶ。
2. Round 1：同じ前提を渡し、他者の意見を見せず独立して検討させる。
3. Round 2：提案を共有し、具体的な根拠・反例・質問を伴う相互レビューを行う。
4. Round 3：反論に回答し、提案を修正するか維持する理由を示す。
5. メインが推奨案、代替案、根拠、合意・対立事項、未検証事項、ユーザーの判断事項を統合する。
6. 批判的レビュー担当が統合結果を確認する。重大な指摘の再検討は最大1回とし、残る問題を明記する。
7. ユーザーに報告し、要件・設計の確定は承認を待つ。

実際のサブエージェントを使用し、単一 Agent の役割演技で代替しない。メインが委譲・結果収集・意見共有を仲介する。起動失敗や未実施工程は明示する。全員参加や多数決を必須にせず、無理に合意させない。事実・仮説・提案・決定を区別し、公開研究・実装の出典を記録する。未検証の性能・新規性を保証しない。

## 設定と成果物
Codex ネイティブ構成を基本とするが既存の構成を優先する。
- AGENTS.md：共通ルール、委譲方針、参照先のみ。
- .codex/config.toml：必要な実行設定のみ。
- .codex/agents/*.toml：個別 Agent 定義。
- .agents/skills/*/SKILL.md：ワークフロー。
- docs/：承認済み要件・設計・決定事項。既存の配置規約に従う。
- worklog/：議論・作業の記録。setup-worklog.md が適用済みならその規約に従う。

通常の単純な質問はメインが回答し、複雑な技術判断やユーザーが議論を求めた場合は専門 Agent を活用する。

## 実行と承認
まず調査し、追加・変更ファイル、役割、実行フロー、既存設定への影響を提示して承認待ちで停止する。承認後に設定を作成し、構文・認識状況を確認する。読み取り専用のサンプル議題で実際の起動、独立検討、意見交換、統合を検証し、実施結果と未検証事項を報告する。
アプリケーション本体の実装、Issue 作成、コミット、push、PR 作成は行わない。機密情報を無断で外部検索やサービスに送らない。回答と文書は日本語を基本とする。
