# Git・GitHub開発ワークフローの構築

現在のプロジェクトに、Issue駆動開発とマルチエージェント開発を組み合わせたGit・GitHub開発ワークフローを構築してください。

## 1. 目的

ユーザーが開発方針および実装計画を承認した後、以下の工程をAIエージェントが自律的に実行できる環境を構築する。

- Issue作成
- ブランチ作成
- 実装
- テスト
- 品質検証
- 独立レビュー
- コミット
- push
- Pull Request作成

最終的なPRの承認とマージは人間が行う。

## 2. 事前調査

- 現在のリポジトリ構成
- AGENTS.md
- 既存のAgent・Skill定義
- 既存の開発ワークフロー
- Gitブランチ構成
- リモートリポジトリ
- デフォルトブランチ
- GitHub CLIの利用可否
- GitHubの認証状態と権限
- 既存のIssue・PRテンプレート
- CI環境
- Codex CLIのバージョンと公式の設定仕様

既存の構成を尊重し、責務が重複するAgent・Skill・ルールを追加しない。

## 3. ブランチ戦略

GitHub Flowを基本とする。

mainを安定ブランチとし、原則としてIssue単位で作業ブランチを作成する。

ブランチの命名形式：

`{type}/{issue-number}-{short-description}`

使用するtype：

- feature：新機能
- fix：不具合修正
- refactor：リファクタリング
- test：テスト
- docs：ドキュメント
- chore：開発環境・設定
- experiment：技術検証・PoC
- hotfix：緊急修正

命名規則：

- 英小文字を使用する。
- 単語の区切りはハイフンとする。
- Issue番号を含める。
- 変更目的が分かる名前とする。
- 原則として最新のデフォルトブランチから作成する。
- mainへの直接コミット・直接pushは禁止する。
- developやreleaseブランチは必要になるまで追加しない。
- 既存の未コミット変更を失わせない。
- 並列実装では必要に応じてGit worktreeを使用する。
- 複数Agentによる同一ファイルの同時編集を避ける。

## 4. Issue管理

実装前に関連Issueを確認する。

既存Issueがある場合は再利用し、同じ課題のIssueを重複して作成しない。

新規Issueには以下を記載する。

- 背景
- 目的
- 対応する要件
- 問題・課題
- 対応範囲
- 対象外
- 実装方針
- 完了条件
- テスト方針
- 依存するIssue
- 未確定事項

Issueは原則として1つの独立した目的を持つ作業単位とする。

複数の独立した目的が含まれる場合は分割する。

Issue作成案と実装計画をユーザーに提示し、承認後にIssueを作成する。

## 5. コミット規約

Conventional Commitsを基本とする。

形式：

`<type>(<scope>): <description>`

使用するtype：

- feat
- fix
- refactor
- test
- docs
- chore
- perf
- ci
- build

コミットは意味のある変更単位で行う。

コミット前に以下を確認する。

- 意図した変更のみ含まれていること
- 不要な生成物が含まれていないこと
- 秘密情報や認証情報が含まれていないこと
- git diff --checkが成功すること
- 必要なテストが成功していること
- 承認済みの実装計画と整合すること

git addによる一括登録は避け、対象ファイルを確認して登録する。

## 6. PR管理

テスト・品質検証・独立レビューが完了した場合にPRを自動作成する。

PRタイトルは以下の形式とする。

`<type>(<scope>): <description> (#<issue-number>)`

PR本文には以下を記載する。

- 変更の目的
- 関連Issue
- 対応する要件
- 変更内容
- 設計上の判断
- テスト・検証結果
- Agentによるレビュー結果
- 指摘への対応結果
- 未解決事項
- 未検証事項
- 互換性への影響

Issueの対応が完了するPRではCloses #番号を記載する。

部分的な対応の場合はRefs #番号を使用する。

PR作成前に以下を確認する。

- Criticalなレビュー指摘が残っていないこと
- 未対応のWarningとその理由が明示されていること
- 必要なテストが成功していること
- 完了条件を満たしていること
- 不要な差分が含まれていないこと
- ベースブランチとの競合がないこと
- 関連Issueとの整合性が保たれていること

未解決の重大な問題がある場合は通常のPRを作成せず、ユーザーへ報告する。

CIが未完了の場合は、その状態を明示する。CI成功前にマージしない。

## 7. Agentの責務

既存Agentを最大限再利用する。

以下の責務が不足している場合のみ、Agentを追加する。

- project_leader：Issue作成案、実装計画、タスク分解
- software_engineer：実装
- test_engineer：テスト設計・作成
- qa_engineer：検証・品質判定
- code_reviewer：独立したコードレビュー
- release_engineer：Git操作・PR準備・PR作成

release_engineerは原則としてアプリケーションコードを変更しない。

実装担当による自己レビューだけで品質判定を完了しない。

メインエージェントがAgent間の連携と工程を管理する。

## 8. Skillの定義

以下のSkillを基本とする。

- wf-issue：Issue調査、重複確認、起票案作成、承認済みIssueの作成
- wf-branch：ブランチ名の決定、作業ツリーの確認、ブランチ作成
- wf-pr：最終検証、コミット、push、PR作成

既存のflow-developmentにこれらを組み込み、以下の開発フローを実行できるようにする。

1. ユーザーの依頼と承認済み要件の確認
2. 関連Issueの確認
3. 設計・実装計画・Issue案の作成
4. ユーザー承認
5. Issue作成
6. ブランチ作成
7. テスト設計
8. 実装・テスト作成
9. 品質検証
10. 独立レビュー
11. 必要な修正・再検証・再レビュー
12. コミット
13. push
14. PR作成
15. CI状態の確認
16. 完了報告

Step 4の承認後は、承認された作業範囲に限り、原則としてStep 16まで連続して実行する。

個別工程ごとに不要な承認を求めない。

ただし、仕様変更、計画外の変更、権限不足、重大な検証失敗、解決できない競合が発生した場合は停止し、ユーザーの判断を求める。

## 9. Git操作の制約

以下を禁止する。

- mainへの直接コミット・push
- force push
- git reset --hard
- git cleanによる作業ファイルの削除
- 既存の未コミット変更の破棄
- 他のAgentや開発者の作業内容の無断変更
- 承認されていないIssueの作成
- 承認されていない変更のpush
- AIによる自動マージ
- ブランチ保護ルールや権限設定の回避

必要なGitHub権限やサンドボックスの承認は正規の手順で取得する。

ワークフロー上の承認とCodex実行環境の操作権限は区別する。

## 10. CI・GitHub設定

既存環境に応じてCIを整備する。

- ビルド
- Lint
- 静的解析
- ユニットテスト
- 結合テスト
- 必要に応じた性能検証

PRに対するCIを実行できるようにする。

mainのブランチ保護について、以下の設定を提案する。

- PR経由の変更を必須とする。
- 必須CIチェックを設定する。
- 必要に応じて人間によるレビュー承認を必須とする。
- force pushを禁止する。
- ブランチ削除を禁止する。

リモートリポジトリの設定変更は、変更内容を提示し、ユーザーの承認を得てから実施する。

## 11. ログ管理

既存のworklog管理規約に従う。

保存形式：

`worklog/YYYYMMDD_HHMMSS_{議題}.txt`

ユーザーの依頼、Agentへの指示、回答、レビュー、承認、Git操作、Issue番号、コミットSHA、PRのURLを同一議題のログへ時系列で追記する。

専用の複雑なログ管理機構は追加しない。

## 12. 設定ファイル管理

以下を基本とし、既存構成に合わせる。

- AGENTS.md
- .codex/agents/
- .codex/guidelines/git-workflow.md
- .agents/skills/
- .github/ISSUE_TEMPLATE/
- .github/pull_request_template.md
- .github/workflows/

Git操作の共通ルールは一箇所で管理し、AGENTS.mdと各Skillから参照する。

既存のflow-developmentを拡張し、同じ役割の別ワークフローを重複作成しない。

## 13. 作成手順

1. 既存環境の調査
2. ブランチ戦略とGit操作規約の設計
3. Agent・Skillの追加および変更方針の設計
4. Issue・PR・CIの構成設計
5. 変更対象ファイルの提示
6. ユーザー承認
7. 設定ファイルの作成・更新
8. 設定の妥当性確認
9. 外部への書き込みを伴わない動作検証
10. 利用方法と未検証事項の報告

まず構築方針を提示し、承認を待ってください。

今回は開発環境の構築を目的とし、アプリケーション本体の実装や実際のIssue・PR作成は行わないでください。

回答とドキュメントは日本語で記載してください。
