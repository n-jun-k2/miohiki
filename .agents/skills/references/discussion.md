# 共通の議論手順

メインがオーケストレーターとなり、議題の自然文または既存 Markdown パスを読み、関連する agent_log、docs、過去の決定を確認する。既存の決定、仮説、提案を区別し、論点と必要な役割を選択する。ユーザーへのヒアリングが必要なら、不明点を整理して確認する。

1. Round 1: 必要なカスタム Agent を実際のサブエージェントとして並列起動する。各自に共通の議題、関連資料、責務と出力形式を渡し、他者の意見や履歴を見せない。利用可能な同時枠を超える場合は独立したバッチに分け、全回答の回収後に次へ進む。回答には提案・根拠・代替案・リスク・未確定事項・出典を含める。
2. Round 2: 親が各意見を共有し、専門分野から具体的な根拠、反例、問題点、対立点をレビューさせる。
3. Round 3: 親が反論を対象者に渡し、修正または不同意の理由と未解決点を受け取る。Agent 間の連絡は親が仲介する。
4. 親が推奨案と理由、各意見、代替案との比較、合意・対立、採用しなかった案と理由、リスク、未検証事項、ユーザーの判断事項を統合する。多数決で決めず、意見の一致を強制しない。
5. critical_reviewer を実際に起動し統合案をレビューさせる。重大な指摘には最大1回だけ再検討を行い、解消しない指摘を未解決として残す。
6. 議論記録を作成し、ユーザーに報告し判断を待つ。承認を得るまで提案を承認済み要件・設計に昇格しない。

各ラウンドの回答は Agent 名、実施状況、主張、根拠と出典を残す。議論は原則3ラウンドで、最終レビューと最大1回の再検討は別工程。起動できない Agent、未実施のラウンド・レビューは明示し、単一 Agent の役割演技で代替しない。起動や処理が途中で失敗したら利用可能な結果だけを記録し、完了したと偽らない。外部資料は出典を記録し、未検証の性能や新規性を保証しない。

議論ごとに worklog/discussions/<日時>-<議題>/ を作り、agenda.md、round-1.md、round-2.md、round-3.md、conclusion.md、review.md、open-questions.md を親だけが作成・編集する。未実施の工程も理由を記録する。agent_log の現状と索引を更新する。ユーザーが承認した要件は docs/requirements、設計は docs/architecture、調査は docs/research、承認済み判断は docs/decisions に必要に応じて保存し、議論への参照を付ける。既存資料と矛盾する場合は勝手に変更せず論点として扱う。
